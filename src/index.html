What the bridge brings

rbridge stays thin: it does not run its own agent loop. It adds what every application needs around one.

ZAP!

Skills that travel

Agent Skills in a library with digests and trust states, delivered to each runtime for one session only. Import a skills-lock.json or install from a catalog.

Your rules

Policy profiles decide what a runtime may do and ask you only when they should. Every session says plainly what is enforced and what is not.

LOCKED!

An optional sandbox

On Linux, run the runtime where it can only write to the project, or with no network at all. Asked for and unavailable means the task stops.

A paper trail

One audit record per session: runtime, profile, approvals, fallbacks, sandbox. Never your prompts or your code.

Every language

CLI, Go library, Node.js and Python SDKs, a local HTTP API with live events, and an MCP server for other agents.

BOOM!

Sessions that last

Stream every step, answer approvals, switch modes, cancel, resume later. A daemon serves several apps, each seeing only its own work.

How it works

Hand over the task

  1. Findrbridge detects the runtimes and accounts on the machine, without reading credentials.
  2. EquipYour app names its skills; rbridge checks their digests and delivers them for this session only.
  3. GuardThe profile answers what it can, asks your code about the rest, and logs every decision.
  4. DeliverEvents stream as the runtime works. The result comes back as text or as JSON matching your schema.
The code of honour

Rules the hero never breaks

Keys stay yours

rbridge never reads, stores or forwards provider credentials. Each runtime signs in its own way.

Local first

Nothing leaves your machine except what your own runtimes send to their providers.

Nothing bundled

rbridge never installs, modifies or bundles a runtime. It uses the ones you chose.

Honest about limits

Each session lists what is enforced, what relies on the runtime asking, and what is not covered.
